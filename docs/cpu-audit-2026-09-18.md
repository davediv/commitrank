# Workers CPU audit and implementation checklist

Scope: this repository's `commitrank` and `commitrank-sync` Workers. Reviewed
2026-09-18. This supplements the historical [optimization report](cpu-optimization.md).
Production CPU attribution and actual cache hit rates have not been measured.
Local measurements below are not Cloudflare billing measurements.

## Findings

### PNG rendering and Wasm memory

`src/routes/api/card/[username].png/+server.ts` checks KV before loading profile
data and an avatar, building SVG, and calling `src/lib/server/card-png.ts`.
The installed resvg 2.6.2 library is the largest measured CPU consumer.

Local Node 26 benchmark: actual layout/SVG/fonts, synthetic 365-day profile,
no avatar, 640px output, 50 renders with the first five excluded from timing:

| Stage                               | Mean CPU per warm render |
| ----------------------------------- | -----------------------: |
| Build SVG/layout                    |                  0.46 ms |
| Parse SVG/fonts and construct resvg |                  2.91 ms |
| Rasterize                           |                 11.54 ms |
| Encode PNG                          |                  8.13 ms |
| Total                               |                 23.04 ms |

Rasterization and encoding account for about 85% of the measured work.
Preserve the existing 640px output, subsetted fonts, cached font decoding,
once-per-isolate Wasm initialization, and visual appearance.

Neither the renderer nor its rendered image was explicitly freed. Wasm memory
grew from 5.5 MiB to 100.1 MiB across 50 renders; freeing both kept it at 5.5 MiB.
The installed `Resvg` constructor does not register itself with its finalization
registry. PNG output is separately owned and remains readable after cleanup.
Explicit cleanup improves reliability; its production CPU benefit is unmeasured.

### Invalidation and duplicate renders

`sync.ts` invalidates profile, user, and card caches for every selected user,
including unsuccessful syncs and unchanged visible card content. Targeted
invalidation already avoids the older global wipe, but a 24-hour card TTL is
still shortened by the user's next sync. Concurrent misses can duplicate renders.

Reuse must compare all rendered inputs, including ranks, avatar bytes/version,
UTC date and renderer version. Contributions alone are insufficient: another
user's update can alter a rank. A Queue or per-card Durable Object is conditional
on measured duplicate demand; moving computation does not itself save CPU.
Do not regenerate cards nobody requests or extend freshness windows blindly.

### Cache layers and hit-rate measurement

The installed Cloudflare adapter checks `caches.default` before SvelteKit hooks
and caches eligible responses afterward. Hooks also maintain a normalized HTML
cache, resulting in two cache lookups/writes on some requests.

| Layer                  | Existing policy                       | Work avoided                  |
| ---------------------- | ------------------------------------- | ----------------------------- |
| Adapter response cache | Full URL; response TTL                | Framework, KV, D1, rendering  |
| Hook HTML cache        | Normalized page key, 60 seconds       | Page loading and SSR          |
| KV data                | Six hours; invalidated by writes/sync | D1 and data reconstruction    |
| KV card PNG            | 24 hours; invalidated by user sync    | SVG, rasterization, encoding  |
| KV avatar              | Seven days; bounded size variants     | Database/upstream image fetch |

Cached `X-Cache` and `X-Page-Cache` headers can describe the original generation,
not the current lookup. Instrument actual cache branches, including the outer
adapter layer. Hook-only logs cannot observe adapter hits. Cache API hits still
invoke the Worker, are colo-local, and do not use Tiered Cache.

Measure response hits / eligible response lookups, KV hits / KV lookups, and
actual renders / incoming card requests separately. Record route templates,
layer, outcome, deployment, colo, and invalidation reasons using sampled compact
events; correlate with invocation CPU. Track total CPU, count, mean/p50/p95 CPU,
and renders per card/version. Separate scheduled sync from manual `/api/sync`.

Tracking parameters, username casing and equivalent avatar-size parameters can
fragment response entries while KV still hits. Canonicalization must preserve
SvelteKit data parameters, original URL-dependent rendering and CORS checks.
Do not cache rate-limited JSON endpoints ahead of their rate limiter.

An improvement from 90% to 99% card reuse would eliminate 90% of render executions
if every miss renders; that is not a prediction of total app CPU savings.

### Scheduled sync

GitHub's query fetches a year, but sync only uses dates from seven days ago
onward (up to eight dates inclusively). For 75 users, roughly 27,000 daily records
are parsed/flattened/mapped to use at most 600. Add optional GraphQL date bounds
for sync while retaining the default full year for registration.

Sync also transfers every user ID just to count users: replace this with SQL
`COUNT(*)`. Per-date delete calls followed by insert can be batched atomically.
The current positive-only reconciliation fails to clear counts that become zero;
preserve exact date coverage when correcting the write algorithm.
Avatar refreshes started by sync must be awaited or tracked through `waitUntil`.

### Prefix invalidation and database work

Leaderboard invalidation enumerates every matching KV key and launches deletes
for each page. Unbounded page numbers multiply cache entries. Generation keys
could replace enumeration, but publication must handle concurrent writers and
KV eventual consistency. Avoid storing arbitrary empty-page variants first.

Profile ranking aggregates all users across the year and calculates four ranks.
The Worker receives one row, so this is mostly D1 cost/latency, not Worker CPU.
Materialized snapshots are conditional on production evidence and must preserve
tie-breaking, UTC rollover and atomic publication.

The migration schema's username indexes do not match `COLLATE NOCASE`. A local
SQLite query-plan check returned `SCAN users`; a matching non-unique NOCASE index
changed it to an indexed search without changing uniqueness semantics.

### Smaller operations and correctness prerequisites

- KV JSON is parsed and serialized again by API handlers. A synthetic profile
  round trip measured about 0.065 ms; whole-response caching must retain dynamic
  timestamps, cache flags, CORS and rate limiting.
- Username/Twitter regexes are bounded; no major regex bottleneck was found.
- Heatmap computation is bounded and already optimized, about 0.1 ms locally.
- Chart aggregation/sorting executes before the zero-width SSR guard. Move the
  guard before computation without changing rendered output.
- Card output is copied twice on misses. Share one exact-length owned buffer.
- Repetitive sync logs and unconditional avatar downloads are secondary work;
  preserve operational errors and refresh behavior rather than remove blindly.
- Browser timers, canvas downloads and palette filtering are not Worker CPU.
  The palette already fetches lazily. Do not replace Drizzle/Svelte/UI libraries
  without evidence or weaken CSP, validation, CORS or rate limits.
- Homepage partial stats cache `total_contributions_year: 0` under the full
  stats API key. Separate payload contracts or use one complete shared query.
- Registration API inserts the full year without the join action's chunking,
  which can exceed D1's 100 bound parameters per statement.

## Todo and validation ledger

Each completed implementation must include validation and an atomic commit.
Unchecked conditional items require measurements or infrastructure rather than
speculative changes. A checked instrumentation item does not claim a measured
production hit rate. Database migrations must be applied separately to production.

## Validation strategy

Record baseline format/lint/typecheck/tests. For each fix: format changed files,
lint affected code, typecheck and run relevant behavioral regressions; build when
runtime/bundling changes. Record pre-existing failures explicitly. Run the full
suite/build at completion and review the final diff. No production deployment or
remote schema mutation is implied by the local commit workflow.
